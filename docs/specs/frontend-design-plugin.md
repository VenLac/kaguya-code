# 前端设计插件（frontend-design）

状态：已注册为内置插件（默认启用）。第二版：由"推荐方向 + 禁用清单"改为"模型自由选风格，插件提供所选风格的执行指南"。真实任务对比评测尚未执行。范围：纯内容型插件包 `apps/zcode-cli/packages/frontend-design-plugin/`，并在四处登记它的存在（见「分发」），不改运行时、协议与 UI 行为。

## 背景

第一版让模型按"产品类型 → 旋钮 → 审美方向食谱"推导风格，并带一份"廉价感"禁用清单。真实产物（一页 Claude Code 营销页）暴露了问题：

1. 规则在**限制**风格选择，又把食谱里的"签名元素"（幽灵数字、可见网格、超大标题）当成要凑齐的清单，结果是风格表演压过了可用性。
2. 没有针对**所选风格**的执行指导：模型选了一个强风格，却不知道这个风格的成立条件和常见翻车点。
3. 自检是模型自述，没有渲染后的客观测量：成品里导航按钮文字被更高优先级的选择器覆盖成浅灰（几乎不可读），注释却声称 5.8:1。

## 目标

- **风格自由。** 插件不推荐、不禁止任何风格（包括 Brutalist、玻璃拟态、赛博朋克、像素、渐变等）。模型可以选任何风格，也可以自创。
- **选定后给出执行指南。** 每个风格有一份"这个风格怎么做才成立"：核心要素的具体取值、这个风格特有的失败模式及修法、这个风格下仍必须守住的可读性底线。
- **通用只守底线。** 与风格无关的部分只保证"读得懂、用得上"，用结果来表述（访客能否一眼看懂），不规定具体字号上限或元素清单。
- **验证靠测量。** 提供可在渲染页面里运行的测量脚本，输出对比度、最小字号、溢出等客观结果；模型不得自述通过。

## 产品规则

### 触发

- 用户要求新建、重做或美化界面，或做设计评审时，模型加载主 skill `frontend-design`。
- 纯逻辑改动不触发。对已有界面的小修小补只走"沿用"模式。

### 两种模式

| 模式 | 条件                                                   | 行为                                                        |
| ---- | ------------------------------------------------------ | ----------------------------------------------------------- |
| 沿用 | 项目有设计约定（`DESIGN.md`、token、组件库、已有页面） | 读取并严格沿用；新增值来自已有 token；缺 token 时扩展 token |
| 新建 | 没有约定                                               | 走完整流程，包含选风格                                      |

### 选风格的优先级

1. 用户明确说了（"像 Linear""赛博朋克""极简"）→ 用它。
2. 项目已有风格 → 沿用。
3. 都没有 → 模型自己选，并给出一句理由。**没有推荐表、没有禁用项。**

### 风格执行指南（Style Playbook）

- 选定风格后，模型读取该风格的 playbook（`references/styles/<name>.md`）。
- 没有现成 playbook 时（用户给了冷门风格、或模型自创、或混合两种风格），模型按 `styles/README.md` 的"推导方法"自己写出该风格的执行要点，再继续。混合风格必须指定主从。
- 每份 playbook 固定结构：**本质 → 核心要素（字体/色彩/形状/空间/深度/动效/图像）→ 执行要点 → 此风格特有的翻车点与修法 → 此风格下仍必须守住的底线 → 起步 token**。
- playbook 描述"怎么做成立"，不评价"该不该选"。

### 通用底线（craft floor）

与风格无关，用结果表述：

- **首屏可读：** 在 1440×900 与 390×844 下，访客不滚动就能知道这是什么、给谁、下一步做什么。风格可以很响，但这三件事必须在首屏出现。
- **文字可读：** 正文与交互控件上的文字，实测对比度满足 WCAG（正文 ≥ 4.5:1，大字与控件边界 ≥ 3:1）；这是**测量**结果，不是自述。
- **一致：** 全页一套 token，同类元素同一做法。
- **层级：** 任一视图有明确的主次。
- **不断裂：** 无横向滚动、无文字溢出或被遮挡、中文不在词中间断行得难看。
- **状态完整：** 交互元素有 hover、focus-visible、disabled 等必要状态；数据区有 loading/empty/error。

### 流程

0 读上下文 → 1 理解对象与场景 → 2 内容先行 → 3 选风格（自由）并读取其 playbook → 4 Design Brief → 5 先 token 后实现 → 6 渲染并测量 → 7 修正。

**Design Brief**（写第一行 UI 代码前展示，6–8 行，每行一句理由）：对象与场景、所选风格及理由、该风格的 3 个关键执行点（取自 playbook）、字体与配色、间距与形状、首屏计划（标题 / 价值主张 / 主操作 / 产品画面各在哪）、一个记忆点。沿用模式改为"沿用的约定 + 需新增的 token"。

### 不做的事

- 不推荐风格、不设风格禁用清单、不设字号上限。
- 不规定技术栈。原则与 token 用 CSS 变量表达，框架写法放 `stacks.md`。
- 不含运行时代码、MCP、hook、命令、agent。
- 不复制项目的 `DESIGN.md` 或 token 到插件。

## 状态所有者

插件无运行时状态。

| 内容                                | 所有者             | 说明                         |
| ----------------------------------- | ------------------ | ---------------------------- |
| 通用底线、各风格 playbook、测量脚本 | 插件 `references/` | 唯一来源，skill 正文只做路由 |
| 项目的设计约定与 token              | 项目自己的文件     | 插件只读                     |

```
   └─ references/

      ├─ craft-floor.md               # 通用底线与常见执行失误（与风格无关）

      ├─ typography.md
      ├─ color.md
      ├─ components-states.md
      ├─ motion-responsive.md
      ├─ verify-in-browser.md         # 渲染后测量脚本与使用方法
      ├─ review-checklist.md
      ├─ stacks.md
      └─ styles/
         ├─ README.md                 # 如何选、如何混、没有现成 playbook 时如何推导
         └─ <style>.md × N            # 各风格执行指南
```

分发（内置，默认启用），需要同步登记的位置共四处：

1. `apps/zcode-cli/packages/bootstrap/src/app/official-plugin-definitions.ts`：definition 与 `requiredSeedPaths`（须列全 SKILL.md 与全部 reference）。
2. `apps/zcode-cli/packages/cli/scripts/sea-official-plugin-assets.mjs`：SEA 清单（独立的第二份，版本须一致）。
3. `packages/shared/src/plugin-marketplaces.ts`：默认启用名单。
4. `packages/ui/src/lib/builtinSkillI18n.ts`：技能来源识别与描述。

版本变更时 plugin.json、definition、SEA 清单三处同步；新增或删除 reference 时前两处文件清单同步。

## 验收场景

1. **自由选风格：** 要求"做一个落地页"且不指定风格。模型自行选风格并给理由；Brief 中无"推荐风格"套话；任何风格（含 Brutalist、玻璃拟态、赛博朋克）都被接受，不被劝退。
2. **读取 playbook：** 选定的风格有现成 playbook 时，Brief 里的 3 个关键执行点与 playbook 一致。
3. **无现成 playbook：** 用户要求"蒸汽波 + 极简的混合风格"。模型按推导方法写出要点并指定主从。
4. **沿用：** 在本仓库改设置页，先读 `DESIGN.md`，不引入新色值与新字体。
5. **首屏：** 任何风格下，成品在 1440×900 与 390×844 首屏内可见：标题、价值主张、主操作。
6. **测量：** 对一份故意把按钮文字被选择器覆盖的页面运行测量脚本，能报出该按钮低对比度。
7. **断裂：** 无横向滚动；中文标题不把一个词拆开断行。
8. **不触发：** 纯逻辑改动不加载该 skill。
9. **结构：** `plugins validate` 通过；所有 reference 相对路径存在；definition 与 SEA 的文件清单与磁盘一致。

## 评测

用 10 条固定需求（登录页、仪表盘、定价页、设置页、空状态、文档站、移动端列表、数据表格、表单向导、品牌落地页），每条在"启用/不启用"下出图，再各换一种风格重做一次，截图盲评，并运行测量脚本。除胜率外，统计"风格被做成立"的比例（是否出现该风格的典型翻车点）。

## 风险

- playbook 写成"推荐"会重新变成限制：每份只描述怎么做成立，不比较风格优劣。
- 通用底线写成具体上限会再次限制风格：只用结果和实测来表述。
- 文件清单在两处登记，漏改会出现"源码有、安装包没有"：用 SEA 采集器与一致性检查验证。
